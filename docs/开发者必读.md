# 开发者必读：灵辑 (MindScribe) 代码库深度解析

> **警告**：本项目包含多层数据兜底和硬编码逻辑，修改任何“默认内容”时必须同步更新 **4 个不同位置**，否则极易出现“修改不生效”的幻觉。

本文档基于实际调试经验，揭示代码库中隐藏的逻辑流向和维护陷阱。

---

## 1. 数据源的“四重奏”陷阱

这是本项目最容易踩坑的地方。系统中的“默认文档”（如《介绍文档》）并非存储在单一位置，而是分散在四个独立的层级中，且优先级逐级递减。

### 1.1 优先级层级（由高到低）

1.  **前端硬编码 (Highest Priority in Dev Mode)**
    *   **文件**：`app/frontend/dev-mode-app.js`
    *   **变量**：`LOCAL_DOCUMENTS` 对象
    *   **行为**：在“开发者模式”下，前端应用会**直接加载**这里的 JSON 数据，完全绕过网络请求。如果你只修改了后端，这里的内容会像“幽灵”一样持续显示旧版本。

2.  **Service Worker 缓存/兜底**
    *   **文件**：`app/web/worker.js`
    *   **变量**：`defaultContent` (JSON stringified)
    *   **行为**：当请求发送到 Cloudflare Workers 但后端无响应或 D1 数据库未命中时，Worker 会返回这份硬编码数据。浏览器缓存也可能导致这里的内容被优先展示。

3.  **后端 API 默认值**
    *   **文件**：`app/web/api_server.py`
    *   **位置**：`get_documents` 接口中的 `documents.append(...)` 逻辑
    *   **行为**：当 API 被调用且数据库中确实没有相关记录时，Python 代码会构造这份默认列表返回。

4.  **数据库初始化逻辑 (Lowest Priority)**
    *   **文件**：`app/web/d1_document_manager.py`
    *   **逻辑**：`_initialize_default_docs` 方法
    *   **行为**：这是真正写入数据库（D1 或本地文件）的源头。但只有在数据库完全为空，或者触发了强制更新逻辑（如检查到关键词缺失）时，才会执行写入。

### 1.2 维护建议

*   **同步修改**：任何涉及到默认文档内容（如《介绍文档》、《系统提示词》）的变更，**必须**同时修改上述四个文件。
*   **搜索关键词**：修改前，务必在全项目搜索文档标题（如“介绍文档”）或特征字符串（如“欢迎使用灵辑”），确保没有遗漏。

## 2. “双前端”架构实相

MindScribe 表面上是一个应用，实际上包含了两个完全隔离的前端逻辑路径。

### 2.1 试用模式 (Trial Mode)
*   **入口**：`index.html` (通常情况)
*   **逻辑**：依赖 `app.js`。
*   **数据流**：强依赖后端 API (`/api/chat`, `/api/documents`)。
*   **存储**：使用临时的 `session_id`，数据存储在 D1 的试用表中，随时可能被清理。

### 2.2 开发者模式 (Dev Mode)
*   **入口**：`dev-mode.html` (或通过 URL 参数/特定指令触发)
*   **逻辑**：依赖 `app/frontend/dev-mode-app.js`。
*   **本质**：这是一个**富客户端 (Fat Client)** 应用。
*   **特点**：
    *   它几乎是一个独立的 SPA（单页应用）。
    *   它内置了大量数据（如上文所述的 `LOCAL_DOCUMENTS`）。
    *   它对后端的依赖极低，甚至可以在离线状态下通过硬编码数据完整运行“查看”功能。
    *   **陷阱**：不要试图通过修改 `app.js` 来改变开发者模式的行为，它们是两套代码。

## 3. 混合后端架构：Python 与 Workers 的纠缠

项目采用了 Python (FastAPI) 和 Cloudflare Workers 混合的架构，这带来了灵活性，也引入了复杂性。

### 3.1 职责划分
*   **Python (FastAPI)**：负责复杂的业务逻辑、LLM 调用、以及与 D1 数据库的**主要**交互。它是“大脑”。
*   **Cloudflare Workers**：负责静态资源托管、请求代理（Gateway），以及**简单的** D1 读写（作为边缘缓存或降级方案）。它是“手脚”。

### 3.2 同步难题
*   **逻辑重复**：为了实现边缘高性能或离线可用，部分业务逻辑（如“获取文档列表”）在 Python 和 JS (Worker) 中各实现了一遍。
*   **版本割裂**：Python 代码部署在 Render 等容器平台，Workers 部署在 Cloudflare。两者的更新频率可能不一致，导致 API 行为在不同网络环境下表现不同。

## 4. 关键调试技巧

基于上述架构，调试时请遵循以下路径：

1.  **界面没变？** -> 90% 是 `dev-mode-app.js` 或 `worker.js` 中的硬编码没改。
2.  **API 返回旧数据？** -> 检查 `d1_document_manager.py` 是否触发了写入逻辑（检查本地 `app/documents/*.txt`）。
3.  **本地文件没生成？** -> 检查 `.gitignore` 是否忽略了 `.txt` 文件（这是曾发生过的真实事故）。
